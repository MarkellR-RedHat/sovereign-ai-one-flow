Arcade Ideas:
Sovereign AI Multi-Tenancy

Ideas for turning the multi-tenancy blog into a 6-module interactive arcade on OpenShift AI.
Source Blog: "Sovereign AI Needs a Tenancy Model, Not Just a Data Center" by Myriam Fentanes Gutierrez / Lindani Pihri

Blog Summary

The blog argues that sovereign AI is not just about putting servers in-country. It is about isolation, governance, and reversibility -- the ability to leave without breaking operations.

  • Sovereignty = cyber resilience + data safeguarding + reversibility
  • Namespaces alone are weak boundaries between distrusting tenants
  • Hosted control planes = strong isolation without 3x control plane node cost
  • RHOAI on hosted/virtualized clusters = each tenant gets their own AI platform
  • GPU isolation (MIG, vGPU, time-slicing) is the remaining hard problem
  • Confidential computing closes the "data in use" gap

Arcade Modules

Module 1 The Problem with Soft Multi-Tenancy

Show why namespace isolation alone is not sufficient for sovereign AI

  1. Start with a shared OpenShift cluster, two namespaces (tenant-a, tenant-b)
  2. Deploy a simple inference workload in each namespace
  3. Show that both tenants share the same API server, same etcd, same kernel
  4. Demonstrate a scenario where tenant-a's noisy workload (GPU memory pressure, burst inference) degrades tenant-b's performance
  5. Highlight: "This is what an auditor sees -- logically separated, physically shared"
Takeaway: Namespaces are fine for cooperating teams, not for distrusting tenants like a ministry, bank, and hospital on the same platform.
Module 2 Hard Isolation Without the Hardware Tax

Show how hosted control planes make per-tenant clusters economically viable

  1. Show the cost problem: 3 control plane nodes x N tenants x N environments = unsustainable
  2. Provision a hosted control plane using HyperShift -- control plane runs as pods on the management cluster
  3. Attach worker nodes via NodePool API
  4. Pair with OpenShift Virtualization -- workers run as VMs
  5. Compare resource footprint: traditional 3-node control plane vs hosted control plane
  6. Show that each tenant still gets their own API server, etcd, and upgrade cadence
Takeaway: You don't have to choose between strong isolation and cost efficiency anymore.
Module 3 Your Own AI Platform, Inside a Shared Infrastructure

Deploy RHOAI on a hosted cluster and show the tenant gets a full AI stack

  1. Start from the hosted cluster created in Module 2
  2. Install RHOAI on the tenant's hosted cluster
  3. Walk through what the tenant now has: workbenches, pipelines, model registry, vLLM serving
  4. Deploy a model using vLLM-based serving inside the tenant boundary
  5. Show that this is fully isolated from other tenants on the same physical infrastructure
  6. Run an inference request, verify it stays within the tenant's boundary
Takeaway: Each tenant gets their own AI platform -- not a shared namespace, a real cluster with a real AI stack.
Module 4 The GPU Challenge -- Slicing Accelerators Across Tenants

Explore the tradeoffs of GPU multi-tenancy isolation

  1. Show a node with GPUs shared across tenants
  2. Demonstrate three approaches side by side:
    • MIG (Multi-Instance GPU): Strongest isolation, fixed partitioning, less flexibility
    • vGPU: Mediated sharing, moderate isolation
    • Time-slicing: Weakest isolation, best utilization
  3. For each: show the isolation strength, utilization efficiency, and operational complexity tradeoff
  4. Attach a GPU to a hosted cluster nodepool (the 3.5 preview capability)
  5. Run inference on the isolated GPU partition
Takeaway: There is no free lunch with GPU isolation -- but the platform composes multiple primitives to find the right balance.
Module 5 Proving It to the Auditor -- Policy-as-Code

Use Advanced Cluster Management (ACM) to enforce and audit multi-tenancy policies

  1. Define governance policies: data residency, network isolation, resource quotas, tenant separation
  2. Apply policies across a fleet of hosted clusters using ACM
  3. Intentionally violate a policy (e.g., try to route traffic across tenant boundaries)
  4. Show ACM flagging the violation in real time
  5. Generate a compliance report showing all tenants meet the stated posture
Takeaway: Sovereignty is not just architecture -- it is auditable, enforceable policy. ACM makes the claim provable.
Module 6 (Bonus) The Reversibility Test

Prove that the tenant can actually leave -- the exit plan works

  1. Export the tenant's models from the model registry
  2. Export pipeline definitions
  3. Show that everything runs on open-source components (vLLM, KServe, etc.)
  4. Demonstrate that the same workload could be deployed on a different OpenShift cluster (or even upstream Kubernetes)
  5. Highlight: no proprietary lock-in, the tenant owns their stack
Takeaway: A "sovereign" platform you can not exit is just domestic lock-in. Reversibility is the core principle.

Suggested Arcade Flow

For a single linear arcade (one cohesive experience):

Module 1
The Problem → Module 2
Hosted Control Planes → Module 3
RHOAI on Top → Module 5
Policy Enforcement
Modules 4 and 6 work best as standalone deep-dives or bonus tracks.

Narrative Thread

The blog has a strong narrative arc that the arcade should mirror:

  1. Open with the misconception -- "sovereignty = data center location" (Module 1 breaks this)
  2. Show why the old answer fails -- cluster-per-tenant is correct but ruinous (Module 2 solves this)
  3. Make it an AI story -- RHOAI on top turns infrastructure isolation into an AI platform (Module 3)
  4. Be honest about what is hard -- GPU isolation is real engineering, not a checkbox (Module 4)
  5. Make it auditable -- policy-as-code with ACM (Module 5)
  6. Close with the reversibility test -- can the tenant leave? That is the real sovereignty question (Module 6)

Notes for Myriam

  • The blog is really well written -- the narrative builds cleanly from misconception to solution to honest caveats. The arcade should keep that same honesty (especially the "GPUs were not designed as multi-tenant security devices" moment).
  • The agentic AI observability teaser at the end of the blog could be a "coming soon" slide in the arcade -- good hook for future content.
  • Consider whether the arcade target audience is the platform admin (who builds this) or the tenant (who consumes it) -- the blog speaks to both but the arcade steps would be different depending on perspective. Recommendation: platform admin perspective for the arcade, since they are the ones making the architecture decisions.

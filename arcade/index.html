Arcade Ideas:
Sovereign AI Multi-Tenancy

Four ways to turn the multi-tenancy blog into an interactive arcade, so click through each idea and pick what works for your situation.
Source: "Sovereign AI Needs a Tenancy Model, Not Just a Data Center" by Myriam Fentanes Gutierrez / Lindani Phiri
Idea 1

The Full Story

6 Modules 45-60 min Workshop / Deep-Dive Lab

This is the big one. Six modules that walk through the entire argument from your blog, start to finish. You open with why namespace isolation isn't enough for sovereign AI, build up to hosted control planes and RHOAI deployment, tackle the GPU problem honestly, prove it to an auditor, and close with the reversibility test.

The narrative follows your blog's arc pretty closely, and each module has hands-on steps so whoever is going through it is actually doing things rather than reading slides. The whole thing builds on itself because each module picks up where the last one left off.

Modules

Module 1 The Problem with Soft Multi-Tenancy

Show why namespace isolation alone is not sufficient for sovereign AI

  1. Start with a shared OpenShift cluster. Two namespaces, tenant-a and tenant-b.
  2. Deploy an inference workload in each namespace.
  3. Show that both tenants share the same API server, same etcd, same kernel.
  4. Hit tenant-a with a GPU burst (noisy inference load) and watch tenant-b's latency spike.
  5. That's what an auditor sees: components that are logically separated but physically shared.
Takeaway: Namespaces work well for cooperating teams, but they fall short when a ministry, a bank, and a hospital need to share the same platform.
Module 2 Hard Isolation Without the Hardware Tax

Show how hosted control planes make per-tenant clusters economically viable

  1. Show the cost problem: 3 control plane nodes x N tenants x N environments, which quickly becomes unsustainable.
  2. Provision a hosted control plane using HyperShift. Control plane runs as pods on the management cluster.
  3. Attach worker nodes via the NodePool API.
  4. Pair with OpenShift Virtualization so the workers run as VMs.
  5. Compare resource footprint: traditional 3-node control plane vs hosted control plane.
  6. Show that each tenant still gets their own API server, etcd, and upgrade cadence.
Takeaway: Hosted control planes let you get strong isolation and cost efficiency at the same time, so you no longer have to treat them as a tradeoff.
Module 3 Your Own AI Platform, Inside Shared Infrastructure

Deploy RHOAI on a hosted cluster and show the tenant gets a full AI stack

  1. Start from the hosted cluster created in Module 2.
  2. Install RHOAI on the tenant's hosted cluster.
  3. Walk through what the tenant now has: workbenches, pipelines, model registry, vLLM serving.
  4. Deploy a model using vLLM inside the tenant boundary.
  5. Show that this is fully isolated from other tenants on the same physical infrastructure.
  6. Run an inference request. Verify it stays within the tenant's boundary.
Takeaway: Each tenant gets their own AI platform with a dedicated cluster and a complete AI stack, rather than just a shared namespace.
Module 4 The GPU Challenge

Be honest about GPU isolation tradeoffs

  1. Show a node with GPUs shared across tenants.
  2. Walk through three approaches side by side:
    • MIG (Multi-Instance GPU): Strongest isolation, fixed partitioning, less flexibility
    • vGPU: Mediated sharing, moderate isolation
    • Time-slicing: Weakest isolation, best utilization
  3. For each one, show the isolation strength, utilization efficiency, and operational complexity tradeoff.
  4. Attach a GPU to a hosted cluster nodepool (the 3.5 preview capability).
  5. Run inference on the isolated GPU partition.
Takeaway: GPU isolation involves real tradeoffs because GPUs were not originally designed as multi-tenant security devices, but the platform composes multiple primitives to find the right balance for your situation.
Module 5 Proving It to the Auditor

Use ACM to enforce and audit multi-tenancy policies

  1. Define governance policies: data residency, network isolation, resource quotas, tenant separation.
  2. Apply policies across a fleet of hosted clusters using Advanced Cluster Management.
  3. Intentionally violate a policy. Try to route traffic across tenant boundaries.
  4. Show ACM flagging the violation in real time.
  5. Generate a compliance report showing all tenants meet the stated posture.
Takeaway: Sovereignty requires auditable, enforceable policy on top of the architecture, and ACM is what makes those claims provable.
Module 6 The Reversibility Test

Prove the tenant can actually leave

  1. Export the tenant's models from the model registry.
  2. Export pipeline definitions.
  3. Show that everything runs on open-source components (vLLM, KServe, etc.).
  4. Demonstrate that the same workload could be deployed on a different OpenShift cluster, or even upstream Kubernetes.
  5. The tenant owns their stack with no proprietary lock-in.
Takeaway: A "sovereign" platform that you can't exit amounts to domestic lock-in, which is why reversibility serves as the real test of sovereignty.

Notes for Myriam

  • This format is the most faithful to your blog. The narrative builds the same way: misconception, why the old answer fails, the real solution, honest caveats, and the reversibility close. If you want the arcade to feel like a hands-on version of the blog, this format is your best match.
  • Modules 4 and 6 work as standalone deep-dives or bonus tracks if 6 modules feels like too much for one sitting. The core arc is really Modules 1 through 5.
  • The agentic AI observability teaser at the end of your blog could be a "coming soon" slide after Module 6. Good hook for future content.
Idea 2

Before / After

2 Modules 10-15 min Quick Demo / Trade Show

This one uses just two modules. Module 1 shows what happens when you try soft multi-tenancy for AI workloads, where tenants share the namespace, API server, and everything else, so one tenant's GPU burst ends up tanking the neighbor. Module 2 then shows what happens when you do it right with a hosted control plane and RHOAI on top, where each tenant gets their own AI platform.

The whole point is to build contrast by letting the viewer feel the problem firsthand before seeing the solution, since watching something actually go wrong is more convincing than theorizing about what could.

This is the version you show someone who has 10 minutes and needs to understand why this matters, and if they want the full story after that, you can link them to the deep-dive.

Modules

Module 1 The Wrong Way

Make them feel the failure mode

  1. Start with a shared OpenShift cluster with two namespaces and two tenants in a standard setup.
  2. Deploy an inference workload in each namespace. Both are humming along fine.
  3. Tenant-a gets a spike in traffic. GPU memory pressure, burst inference requests.
  4. Watch tenant-b's response times fall apart even though their workload didn't change, because the shared infrastructure means the performance impact bleeds over.
  5. Show the shared components—same API server, same etcd, same kernel, same GPU node—to demonstrate what "logically separated, physically shared" actually looks like when it breaks.
  6. Pull up what an auditor would see: two namespaces that look fine on paper but don't hold up in reality.
Takeaway: Namespaces work well for cooperating teams, but for distrusting tenants running sovereign AI workloads, they aren't sufficient, as this module just demonstrated.
Module 2 The Right Way

Same infrastructure, real isolation, full AI stack

  1. Same physical infrastructure. This time, provision a hosted control plane using HyperShift.
  2. Each tenant gets their own cluster with a dedicated API server and etcd, but the control plane runs as pods on the management cluster so you're not burning 3 control plane nodes per tenant.
  3. Install RHOAI on the tenant's hosted cluster, which gives them the full stack: workbenches, pipelines, model registry, and vLLM serving.
  4. Deploy a model. Run an inference request. All within the tenant's boundary.
  5. Hit tenant-a with the same burst from Module 1 and show that tenant-b's performance remains completely unaffected.
  6. Show the compliance view: ACM policies enforced, tenant boundaries auditable, data residency verifiable.
Takeaway: Each tenant gets a full AI platform with strong isolation and without the hardware tax, and you can prove all of it to an auditor, which is exactly the architecture your blog proposes.

Notes for Myriam

  • This format is built around contrast, where the person going through it should feel Module 1 break and then feel Module 2 work, since that emotional arc is what makes the message stick.
  • Best fit for a booth demo, a hallway conversation at Summit, or as the first thing you show someone who doesn't have context yet, since it works well as a hook into the deeper content.
  • You could always end Module 2 with a "want the full deep-dive?" link that points to the 6-module version.
Idea 3

Pick Your Role

3 Tracks 15-25 min each Self-Service / RHDP Catalog

Different audiences care about different aspects of this: a platform admin wants to know how to build it, a tenant wants to know what they get, and an auditor wants to know how to verify it.

This approach gives each persona their own 2-3 module track where they pick their role at the start and only see what's relevant to them, all running against the same underlying infrastructure but viewed through a different lens.

Your blog speaks to all three audiences, and this format lets each one get exactly what they need without sitting through the parts that aren't for them.

Track A: Platform Admin

The person who builds and operates the multi-tenant infrastructure.

Module A-1 Build the Foundation

Set up hosted control planes and tenant isolation

  1. Start from a management cluster. Provision hosted control planes using HyperShift.
  2. Create two tenant clusters. Show the resource footprint compared to traditional 3-node control planes.
  3. Configure node pools with OpenShift Virtualization. Workers run as VMs for stronger isolation.
  4. Set up GPU partitioning across tenant clusters (MIG, vGPU, or time-slicing depending on the isolation requirement).
  5. Configure network policies so tenants can't reach each other.
Takeaway: You can provide each tenant with full cluster-level isolation without paying the 3x control plane cost per tenant.
Module A-2 Deploy the AI Stack

Install RHOAI on tenant clusters and configure fleet governance

  1. Install RHOAI on each tenant's hosted cluster.
  2. Configure model serving with vLLM per tenant.
  3. Set up ACM policies: data residency, resource quotas, tenant separation.
  4. Apply policies across the fleet. Show that violations get flagged in real time.
  5. Generate the compliance report an auditor would need.
Takeaway: As the admin, you deploy once and govern at fleet scale. ACM turns your architecture claims into provable policy.

Track B: Tenant

The data scientist or ML engineer who consumes the platform.

Module B-1 Your AI Platform

Show what the tenant gets and how they use it

  1. Log in to the RHOAI dashboard on your hosted cluster.
  2. Tour the tools: workbenches for notebooks, pipelines for automation, model registry for versioning.
  3. Deploy a model using vLLM. Run a few inference requests.
  4. Show that you have your own model registry, your own pipeline server, and your own serving endpoints, which makes this a dedicated platform rather than a shared namespace.
  5. Try to access tenant-b's resources to confirm that the isolation boundaries are enforced.
Takeaway: From the tenant's perspective, this is their own AI platform. They don't share it and they don't have to worry about noisy neighbors.
Module B-2 The Exit Plan

Prove portability

  1. Export models from the model registry.
  2. Export pipeline definitions.
  3. Show that everything is open source: vLLM, KServe, standard Kubernetes APIs.
  4. Demonstrate that the same workload could run on upstream Kubernetes if needed.
Takeaway: Everything you built here is portable and free of lock-in, which is what reversibility means in practice.

Track C: Auditor / Compliance

The person who needs to verify the claims.

Module C-1 Verify the Isolation

Prove that tenant separation is real, not just RBAC

  1. Start with the running multi-tenant environment.
  2. Show what makes this different from namespace isolation: separate API servers, separate etcd, separate certificate authorities.
  3. Attempt cross-tenant access. Network policies, RBAC, and cluster boundaries all block it.
  4. Review the ACM compliance dashboard. Every policy, every cluster, every violation logged.
  5. Generate the compliance report. Data residency, GPU isolation mode, network segmentation, all verifiable.
Takeaway: The isolation is provable, auditable, and enforceable through policy-as-code, which gives you something concrete to present to the auditor.

Notes for Myriam

  • This format works best if you're thinking about the RHDP catalog where people self-serve. They pick their role and get a focused experience. No one has to sit through the parts that aren't for them.
  • Track A (Platform Admin) is probably the primary audience based on your blog, since it reads like it's written for the person making the architecture decision, but Track C (Auditor) is especially valuable because that's who the platform admin needs to convince.
  • You could combine this with the Before/After (Idea 2) as a shared intro module before people pick their track. "Here's the problem—which angle do you want to explore?"
Idea 4

Just Show Me

1 Module 5 min Executive Briefing / Hallway Demo

This is a single module that provisions a hosted cluster, installs RHOAI, deploys Granite, runs an inference request, and proves tenant-b can't see tenant-a's resources.

It skips setup modules, theory, and "first let's understand the problem" framing in favor of showing the thing working, and you can always link to the full walkthrough for people who want the context.

This is the version for when someone says "I have 5 minutes, show me why I should care," because it demonstrates the value rather than explaining it.

The Module

Single Module Sovereign AI Multi-Tenancy in 5 Minutes

Show the whole value proposition in one shot

  1. Start from a management cluster with HyperShift already running.
  2. Provision a hosted cluster for tenant-a and show how the control plane runs as pods, which eliminates the 3-node hardware tax.
  3. Install RHOAI on tenant-a's cluster. Quick tour: workbenches, model registry, vLLM serving.
  4. Deploy Granite (small, open, fast). Run an inference request.
  5. Switch to tenant-b's cluster and try to access tenant-a's model endpoint and model registry, confirming that neither is reachable across the tenant boundary.
  6. Show the ACM dashboard. Both tenants compliant, boundaries enforced, audit trail clean.
  7. Close: "Everything here runs on open source. The tenant can export their models and pipelines and leave whenever they want. That's the reversibility promise."
Takeaway: This covers the entire pitch—full AI platform isolation, cost efficient infrastructure, auditable compliance, and portability—demonstrated as a working system rather than a slide deck.

Notes for Myriam

  • This is your elevator pitch as an arcade. Step 1 in the management cluster assumes HyperShift is pre-installed, which saves a few minutes of setup that doesn't add to the story.
  • Granite is a good choice for the demo model because it's small, open, and Red Hat publishes it on Hugging Face, which makes it fast to deploy and serve without any licensing questions.
  • If someone finishes this and wants more, you link them to either the Before/After (Idea 2) for the "why" or the Full Story (Idea 1) for the deep dive.
